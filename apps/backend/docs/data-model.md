# Data model

## Tables

All IDs are UUIDs generated by the app. Amounts, quantities, prices and rates are
`numeric(30,10)`. The app handles them as decimal.js values, and the API sends
them as decimal strings such as `"1234.5"`. JavaScript numbers are never used
for money.

### `users`

| Column | Notes |
|---|---|
| `id` | Money's user ID |
| `issuer`, `subject` | `iss` and `sub` of the Taico token. **Unique together**: this is the identity. |
| `display_name`, `email` | Copied from the token on each call. Informational only. |

### `accounts`

| Column | Notes |
|---|---|
| `user_id` | Owner (FK, cascade) |
| `name` | Unique among siblings, case-insensitive (`UQ_accounts_user_parent_name` on `(user_id, coalesce(parent_account_id, nil-uuid), lower(name))`) |
| `parent_account_id` | The account this is a subaccount (bucket) of, or null. Composite FK `(parent_account_id, user_id) → accounts(id, user_id)`, so it is always the same user's account. At most 5 levels; no cycles (see [categories.md](categories.md)). |
| `category_id` | The account's own category, or null (inherits its parent's). Composite FK to `categories(id, user_id)`, `ON DELETE SET NULL (category_id)` (needs Postgres 15+). |
| `type` | `INVESTMENT` (the main case), `CASH`, `SUPERANNUATION` (retirement savings: everything in it and its subaccounts is the dashboard's "super" asset class, see [dashboard.md](dashboard.md)) or `OTHER`. Named CHECK `CHK_accounts_type`. |
| `reporting_currency` | The currency the account is usually reported in. Cash can be held in any currency. |
| `description` | Free text |

### `categories`

User-defined labels (`name` unique per user, case-insensitive; optional
`description` and `#rrggbb` `color`). `(id, user_id)` is unique so other tables
can reference it with a composite FK.

### `holding_categories`

One row per holding that has its own category. The key is `(account_id,
symbol)`, so there is at most one category per holding. `user_id` and the
composite FKs to `accounts` and `categories` keep both on the same user. The
row is deleted with the account or the category.

### `transfers`

A transfer between two of the user's accounts: `from_account_id`,
`to_account_id` (composite FKs to `accounts(id, user_id)`, NO ACTION, so an
account in a transfer can't be deleted on its own), `date`, `description`,
`from_currency`, `from_amount`, `to_currency`, `to_amount`, `fx_rate` (to per
from), `fees` (in from currency) and `calculated_field`. CHECKs: the two
accounts differ, amounts and rate are positive, and within one currency
`to_amount = from_amount` and `fx_rate = 1`. See [transfers.md](transfers.md).

### `transactions`

One row per recorded activity. `user_id` repeats the account owner so every query
can filter on the user directly. `sequence` is the per-account insertion order
(unique per account) and breaks ties between transactions on the same `date`.

| Type | Columns used | Cash effect |
|---|---|---|
| `DEPOSIT` | `currency`, `amount`; optional `external_currency`, `external_amount` | `+amount` in `currency` |
| `WITHDRAWAL` | same as `DEPOSIT` | `−amount` in `currency` |
| `FX_CONVERSION` | `from_currency`, `from_amount`, `to_currency`, `to_amount`, `fx_rate`, `fees` (in from currency) | `−(from_amount + fees)` from, `+to_amount` to |
| `BUY` | `symbol`, `currency`, `quantity`, `unit_price`, `fees`, `total` (= q × p + fees) | `−total` |
| `SELL` | same as `BUY`, but `total` = q × p − fees; `lot_selection` (`FIFO` or `SPECIFIC`) | `+total` |
| `DIVIDEND` | `symbol`, `currency`, `gross_amount`, `withholding_tax`, `net_amount`, `franking_credits` | `+net_amount` |
| `TRANSFER_OUT` | `currency`, `amount`, `fees`, `transfer_id`, `counterparty_account_id` | `−(amount + fees)` |
| `TRANSFER_IN` | `currency`, `amount`, `transfer_id`, `counterparty_account_id` | `+amount` |

Transfer legs exist only as a pair owned by a `transfers` row. A CHECK requires
`transfer_id` and `counterparty_account_id` on legs and forbids them on every
other type. `UQ_transactions_transfer_leg` allows one leg of each kind per
transfer. Composite FKs keep the transfer and the counterparty with the same
user. Deleting the transfer cascades to its legs.

`external_*` on deposits and withdrawals describe the other side outside the
account, for example "1000 AUD left the bank and arrived as 650 USD". They are
informational and don't change any balance.

`calculated_field` records which field Money worked out from the others:

- trades: one of `quantity`, `unitPrice`, `fees`, `total` (three of four given);
- dividends: one of `grossAmount`, `withholdingTax`, `netAmount` (two of three given);
- FX: one of `fromAmount`, `toAmount`, `rate` (two of three given).

It is `null` when every field was supplied. CHECK constraints require the
columns each type needs.

### Sale lot allocations

`sale_lot_allocations` stores, for each `SPECIFIC` sale, the shares it took
from each lot: `(sale_transaction_id, lot_transaction_id, position,
quantity > 0)`. A lot is its BUY transaction. Composite FKs to
`transactions (id, user_id, account_id)` keep the sale and the lot with the
same user and account. The sale FK cascades. The lot FK is deferred to commit,
so a referenced purchase can't be deleted on its own, while account and user
deletion still cascade. `lot_selection` is set on SELLs only, and the
migration backfilled `FIFO` on existing ones. See
[lot-selection.md](lot-selection.md).

### Daily valuations

`valuation_days`, `valuation_holdings`, `market_price_closes`,
`valuation_recompute_requests` and `valuation_job_state` hold the daily
closing-price valuations: materialised snapshots of derived state, written
only by the valuation job and always recomputable from the ledger plus closes.
Holding rows have composite FKs to `accounts(id, user_id)` (cascade) and to
their `valuation_days` row. A trigger on `transactions` records backdated
BUY/SELL changes for recomputation. See [valuations.md](valuations.md).

`market_price_closes`, `market_price_series` and `market_price_splits` are the
shared, store-first price history: market data, not per user, keyed by
`(symbol, source)`. Closes are stored as traded (`adjustment = 'AS_TRADED'`).
See [market-prices.md](market-prices.md).

## Derived state: replayed, never stored

Cash per currency, lots (parcels), holdings, cost bases, realized gains and
dividend totals are **not stored**. `replayLedger` (`src/ledger/ledger-engine.ts`)
derives them by replaying an account's transactions in `(date, sequence)` order.
At personal scale (thousands of rows per account) the replay costs very little,
and stale balances become impossible.

During the replay, the first transaction that does any of the following raises a
`ledger_violation` (HTTP 422), naming that transaction:

- makes a currency's cash balance negative (no margin or overdraft);
- sells more shares than are held at that date;
- has lot allocations that don't fit the lots at that point (see [lot-selection.md](lot-selection.md));
- trades a ticker in a second currency within the same account.

Dividends don't require the ticker to be held, because they can arrive after a
sale.

## Write semantics

Every create, edit and delete runs in one database transaction:

1. lock the account row (`SELECT … FOR UPDATE`);
2. load all of the account's transactions;
3. apply the change in memory;
4. replay the ledger;
5. write only if the replay succeeds.

So:

- **Creates** append with the next `sequence`. A back-dated transaction is
  replayed at its date.
- **Edits** keep the type, account and `sequence`. Fields left out keep their
  value. The field Money calculated before is recalculated from the new values
  unless the edit supplies it. Setting a calculable field to `null` asks for it
  to be recalculated. Fields that don't apply to the type are refused.
- **Deletes** are refused when later transactions depend on the row, for
  example deleting the deposit that funded a buy, or a buy whose shares were
  later sold. Delete or edit the dependants first.
- **Account deletion** is refused while the account has transactions, unless
  `deleteTransactions=true` is passed; the transactions are then deleted with
  it.
- Concurrent changes to one account are serialized by the row lock. A test runs
  five parallel withdrawals against Postgres to check this.

Moving a transaction to another account isn't supported: delete it and record
it again.

- **Transfers** lock both accounts in id order and replay both ledgers before
  writing the transfer and its two legs. A leg can't be edited or deleted on
  its own, and an account that takes part in transfers can't be deleted. See
  [transfers.md](transfers.md).

- **Hierarchy changes** (creating, moving or deleting an account) lock the
  user's row before the account row. Concurrent moves are serialized, so
  they can't create a cycle together.

### Lock order

Every writer takes locks in this order, and skips the ones it doesn't need:

1. the user row (`FOR UPDATE`): hierarchy changes only;
2. a category row: `FOR SHARE` to assign it to an account or holding,
   `FOR UPDATE` to delete it;
3. account rows (`FOR UPDATE`): one account for a transaction write or an
   account update/delete; **both accounts of a transfer, in id order**; when a
   category is deleted, every account it affects (directly, or through a
   holding), in id order.

Postgres takes the ON DELETE SET NULL / CASCADE actions of a category delete
on the account rows. Without step 3 up front, a delete holding the category
would wait for an account that an assignment holds while that assignment waits
for the category: a deadlock. `src/category-locking.e2e.spec.ts` forces that
interleaving against real Postgres. New writers must keep this order. The valuation job takes no row locks on
accounts, users or categories: it reads committed ledgers and replaces its own
snapshot rows, and relies on recompute requests (written by the
`transactions` trigger inside the writer's transaction) to catch changes that
race a run.
Transfers do: they lock only their two accounts, in id order, and
`src/transfers.e2e.spec.ts` runs opposite-direction transfers concurrently
against Postgres to check they don't deadlock.
